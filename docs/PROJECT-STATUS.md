# وضعیت پروژه هم‌نور

آخرین به‌روزرسانی: ۱۵ ژوئیه ۲۰۲۶

## معرفی محصول

«Hamnoor | هم‌نور» یک افزونه فارسی و راست‌به‌چپ وردپرس برای ایجاد و مدیریت ختم‌های جمعی قرآن است. کاربران می‌توانند ختم عمومی یا خصوصی بسازند، سهم بگیرند، قرائت را ثبت کنند و مشارکت‌های خود را پیگیری کنند. مدیران نیز انتشار، ختم‌های ویژه، تنظیمات، گزارش و خروجی را مدیریت می‌کنند.

## معماری کلی

- `hamnoor.php` bootstrap، ثابت‌های نسخه و بارگذاری اجزای افزونه را انجام می‌دهد.
- `Hamnoor_DB` مالک schema، migration و SQL متمرکز هسته است.
- Repository و Service برای ختم، سهم و شرکت‌کننده مرز دسترسی دامنه را فراهم می‌کنند.
- Frontend و Admin کنترلرهای اصلی درخواست‌ها هستند؛ AJAX فرانت‌اند فعلاً در Frontend controller قرار دارد.
- Router صفحات مجازی ختم را به URLهای کوتاه متصل می‌کند.
- REST API، Export، SEO، Validator، Permissions، Text manager، Notification service و Featured service اجزای مستقل‌اند.
- templateهای فرانت‌اند در `templates/frontend` و assetهای scoped در `assets` قرار دارند.

## جداول دیتابیس

نام واقعی جدول‌ها با `$wpdb->prefix` ساخته می‌شود:

| جدول منطقی | مسئولیت |
|---|---|
| `hamnoor_khatms` | ختم، مالک، ساختار، انتشار، ظاهر، ویژه‌سازی و سیاست قرائت |
| `hamnoor_parts` | سهم‌ها و چرخه available/claimed/done/release |
| `hamnoor_participants` | هویت مشارکت‌کننده در محدوده ختم و tracking token |
| `hamnoor_logs` | audit پایه عملیات |
| `hamnoor_otps` | OTP اختیاری، انقضا و مصرف |

foreign key فیزیکی استفاده نمی‌شود؛ integrity در لایه برنامه، transactionها و عملیات شرطی کنترل می‌شود.

## نقش ابزارها و سرویس‌ها

- **مالک محصول:** تصمیم نهایی درباره دامنه قابلیت، متن‌های حساس و انتشار سایت اصلی.
- **ChatGPT Project:** نگهداری زمینه بلندمدت محصول، تصمیم‌ها، وضعیت و برنامه‌های تأییدشده.
- **Codex:** بررسی مخزن، اجرای تغییرات محدود، آزمون، مستندسازی و گزارش شفاف؛ مطابق `AGENTS.md`.
- **GitHub:** منبع تاریخچه، شاخه اصلی، commitها، tagها و artifactهای انتشار در صورت انتشار Release.
- **Local:** محیط اجرای WordPress/MySQL برای migration، HTTP، REST و smoke test؛ نه منبع حقیقت کد.

Git و کد فعلی منبع حقیقت هستند. داده Local فقط برای آزمون است.

## مشکلات شناخته‌شده و کارهای باز

- اسناد معماری ریشه هنوز عنوان و وضعیت 2.6.0/Release Candidate دارند؛ تصمیم‌های پایه معتبرند اما وضعیت جاری محسوب نمی‌شوند.
- `ORDER BY RAND()` برای انتخاب تصادفی در dataset بسیار بزرگ ممکن است پرهزینه شود؛ اقدام فقط پس از مشاهده نیاز عملیاتی پیشنهاد می‌شود.
- uniqueness تماس participant در concurrency بسیار بالا با constraint دیتابیسی کامل مدل نشده است؛ پیشنهاد `identity_hash` نیازمند داده و تصمیم migration است.
- rate limit مبتنی بر transient در استقرار چندسروری بدون object cache مشترک دفاع سراسری نیست.
- XLSX به `ZipArchive` وابسته است و در نبود آن به CSV fallback می‌کند.
- AJAX هنوز در Frontend controller و بخشی از HTML در همان کنترلر است؛ refactor صرفاً با دلیل و پوشش regression انجام شود.
- matrix واقعی نسخه‌های PHP/WordPress، آزمون دیداری قالب کلاسیک/بلوکی و integration با افزونه‌های SEO نیازمند برنامه آزمون مستمر است.
- وضعیت GitHub Release نسخه 2.8.0 نیازمند تأیید مالک محصول است.
