# تصمیم‌های معماری هم‌نور

آخرین به‌روزرسانی: ۱۵ ژوئیه ۲۰۲۶

وضعیت‌ها: **فعال**، **منسوخ** یا **نیازمند بازبینی**.

## ۱. جداول اختصاصی برای داده دامنه

- **تصمیم:** ختم‌ها، سهم‌ها، شرکت‌کنندگان، لاگ‌ها و OTP در پنج جدول اختصاصی با prefix وردپرس ذخیره می‌شوند.
- **دلیل:** حجم، query، lifecycle و گزارش این موجودیت‌ها با post/meta عمومی وردپرس هم‌خوانی کامل ندارد.
- **پیامد:** schema و migration باید با `dbDelta()`، query آماده و سازگاری نسخه‌های قبلی مدیریت شوند. foreign key فیزیکی استفاده نمی‌شود و integrity مسئولیت لایه برنامه است.
- **وضعیت:** فعال.

## ۲. Router و صفحات مجازی ختم

- **تصمیم:** صفحه ختم با query var و Router روی URL مجازی نمایش داده می‌شود؛ مسیر کوتاه اصلی `/h/{token}/` است و مسیرهای slug/legacy حفظ می‌شوند.
- **دلیل:** URL پایدار و کوتاه بدون نیاز به ساخت post برای هر ختم.
- **پیامد:** rewrite، canonical، shortlink، template و سازگاری قالب باید با هم آزموده شوند. حذف مسیر قدیمی بدون migration لینک مجاز نیست.
- **وضعیت:** فعال.

## ۳. Token و لینک کوتاه

- **تصمیم:** توکن ختم‌های جدید ۱۲ کاراکتری است؛ sanitizer حروف انگلیسی، عدد، خط تیره و underscore را برای سازگاری می‌پذیرد. لینک دعوت از helper مرکزی ساخته می‌شود.
- **دلیل:** آنتروپی بهتر برای ختم‌های جدید و یکسان‌بودن UI، REST، share، canonical و shortlink.
- **پیامد:** tokenهای قدیمی rotate نمی‌شوند و URL موجود شکسته نمی‌شود. token و tracking token نباید در خروجی یا log نامجاز افشا شوند.
- **وضعیت:** فعال.

## ۴. Repository و Service

- **تصمیم:** Khatm، Part و Participant دارای Repository و Service هستند؛ SQL اصلی فعلاً در `Hamnoor_DB` متمرکز است.
- **دلیل:** ایجاد مرز دامنه بدون refactor پرریسک کل persistence.
- **پیامد:** کنترلرها باید از Service/Repository استفاده کنند؛ abstraction فعلی نازک است و انتقال بیشتر فقط تدریجی و با آزمون regression انجام می‌شود.
- **وضعیت:** فعال؛ عمق abstraction نیازمند بازبینی در صورت توسعه بزرگ.

## ۵. REST و AJAX

- **تصمیم:** REST در namespace نسخه‌مند `hamnoor/v1` ارائه می‌شود؛ endpoint عمومی DTO محدود و endpoint مدیریتی permission callback دارد. تعاملات فرانت‌اند از AJAX وردپرس و admin-post استفاده می‌کنند.
- **دلیل:** پشتیبانی integration و UX تعاملی در کنار fallbackهای وردپرس.
- **پیامد:** nonce، rate limit، capability/ownership، sanitization و عدم افشای contact یا tracking token الزامی است. AJAX فعلاً در Frontend controller باقی مانده است.
- **وضعیت:** فعال؛ جداسازی AJAX نیازمند بازبینی است، نه الزام فعلی.

## ۶. ذخیره تنظیمات

- **تصمیم:** تنظیمات عمومی در option آرایه‌ای `hamnoor_settings` و متن‌های قابل ویرایش در option مستقل نگهداری می‌شوند؛ defaultها در helper/text manager ادغام می‌شوند.
- **دلیل:** استفاده از WordPress Options API و جلوگیری از جدول تنظیمات اضافی.
- **پیامد:** نام optionها قرارداد سازگاری‌اند؛ ذخیره تب تنظیمات نباید مقادیر تب‌های دیگر را حذف کند. credential ادان‌ها نباید در option عمومی هم‌نور ذخیره شود.
- **وضعیت:** فعال.

## ۷. Migrationها

- **تصمیم:** migration عمومی با `HAMNOOR_DB_VERSION` و عملیات idempotent اجرا می‌شود. migration محدودیت تکرار سوره option مستقل `hamnoor_repeat_limit_schema_version` دارد.
- **دلیل:** ستون `max_repeat_count` باید بدون افزایش غیرضروری نسخه اصلی دیتابیس و با قابلیت اجرای تکراری امن اضافه شود.
- **پیامد:** نسخه افزونه می‌تواند از نسخه دیتابیس متفاوت باشد. هر migration جدید باید versioned، repeatable، non-destructive و دارای برنامه rollback باشد.
- **وضعیت:** فعال.

## ۸. سیاست دسترسی و capability

- **تصمیم:** مدیر وردپرس و capability `hamnoor_manage_all_khatms` کنترل کامل دارند؛ نقش `hamnoor_manager` capabilityهای ایجاد ختم و مدیریت ختم خود را دارد. مالکیت رکورد به‌تنهایی جای capability را نمی‌گیرد.
- **دلیل:** تفکیک مدیر کل، ایجادکننده و مشارکت‌کننده و جلوگیری از ارتقای ناخواسته دسترسی.
- **پیامد:** هر endpoint باید nonce/authentication و capability یا مالکیت scoped را بررسی کند. owner نمی‌تواند override مدیریتی محدودیت تکرار را تغییر دهد.
- **وضعیت:** فعال.

## ۹. حفظ سازگاری داده‌های قبلی

- **تصمیم:** schema، option، URL، token، shortcode، action/filter و داده موجود بدون migration صریح حذف یا بازنویسی نمی‌شوند.
- **دلیل:** ختم‌ها و لینک‌های دعوت ممکن است بلندمدت و عمومی باشند.
- **پیامد:** ختم قدیمی با تعداد تکرار بالاتر از سقف جدید قابل ویرایش/حفظ است؛ مسیرهای legacy و hookهای قدیمی تا تصمیم نسخه‌ای روشن باقی می‌مانند.
- **وضعیت:** فعال.

## ۱۰. مرز هسته و ادان

- **تصمیم:** قابلیت provider-specific یا تجاری مانند SMS، queue، reminder، QR، analytics، payment و template pack در ادان مستقل قرار می‌گیرد. هسته lifecycle hook و notification provider interface می‌دهد.
- **دلیل:** جلوگیری از credential و dependency تجاری در هسته و حفظ قابلیت حذف مستقل ادان.
- **پیامد:** ادان نباید فایل یا جدول هسته را patch کند، endpoint هسته را monkey patch کند یا وضعیت سهم را مستقیم بنویسد.
- **وضعیت:** فعال.

## ۱۱. پیگیری ساده و OTP اختیاری

- **تصمیم:** پیگیری تماس‌محور ساده در تنظیم پیش‌فرض قابل استفاده است و زیرساخت OTP اختیاری در هسته وجود دارد.
- **دلیل:** کاهش اصطکاک مشارکت عمومی، همراه با امکان افزایش assurance برای سایت حساس.
- **پیامد:** این انتخاب assurance کمتری از OTP اجباری دارد و باید همراه rate limit و تطبیق contact باقی بماند.
- **وضعیت:** فعال؛ سیاست پیش‌فرض نیازمند تصمیم مالک محصول در هر استقرار حساس.

## ۱۲. توسعه با GitHub، Codex و Local

- **تصمیم:** Git و کد منبع حقیقت‌اند؛ Codex تغییر محدود و قابل بازبینی انجام می‌دهد؛ Local محیط اجرای WordPress است؛ GitHub تاریخچه و انتشار را نگه می‌دارد.
- **دلیل:** جداسازی روشن کد، automation، محیط آزمایش و تصمیم محصول.
- **پیامد:** قبل از تغییر، diff و وضعیت Git بررسی می‌شود؛ پس از تغییر آزمون متناسب اجرا می‌شود؛ commit/push فقط با درخواست صریح انجام می‌شود؛ داده Local وارد مخزن یا ZIP نمی‌شود.
- **وضعیت:** فعال.
